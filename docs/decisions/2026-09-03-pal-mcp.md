# PAL MCP integration + `code-reviewer` retirement — outcome (3 Sep 2026)

Decision record for the work that implemented the PAL handoff brief. Shipped as `claude-code-unraid`
**0.23**, CI run `33754102370` green, force-updated and verified live the same day. Container ops
facts live in `OPERATIONS.md` and the AWS provider record in `pal-bedrock-provider-setup.md` — not
repeated here.

Corrections applied to the brief before starting: the Bedrock console "request model access" step is
retired (serverless models auto-enable), and this is **Bedrock-only** — the OpenRouter leg was
dropped, not deferred.

## Behaviour before vs after

**Before.** Review was Claude reviewing Claude's own output. The only reviewer was
`code-reviewer@dotclaude`, a third-party marketplace plugin (v2.1.0, `poshan0126/dotclaude`): a
generic team-oriented rubric — correctness, error handling, **naming**, **complexity** (function
length, nesting depth, parameter counts) and tests, with a ≥80 confidence filter and terse one-line
output. It had **no** security axis, **no** brief-conformance axis, and **no** omissions check
against a previous implementation. No non-Claude model was in the review path at all.

**After.** Three reviewers, deliberately not merged, plus two deliberately-invoked specialists:

| Reviewer | Runs where | Covers |
|---|---|---|
| `@code-reviewer` (local, `~/.claude/agents/code-reviewer.md`) | Claude, in-session | Axis A works-first-go incl. omissions/parity, Axis C fits-the-brief |
| PAL `consensus` — `zai.glm-5` + `deepseek.v3.2` | Bedrock ap-southeast-2 | Axis A, Axis B security, from a non-Claude lineage |
| `advisor` (Fable) | built-in, final pass | Triage: rank, identify genuine contests, drop what fails scrutiny |
| `@silent-failure-hunter` | Claude, on explicit request | Exhaustive error-path audit — narrower but far deeper than Axis A |
| `@pr-test-analyzer` | Claude, on explicit request | Test coverage quality and completeness on a PR |

Naming, function length and readability-for-a-team are gone from the rubric by design —
single-maintainer project. PAL is an advisor only and has no repository write access.

## Advisor's verdicts on the four open questions

Each working default was put to `advisor` (Fable) before being locked in.

**Q1 — bake into the image under `/opt`.** *Agree.* Runtime install would add network-at-start
latency against the SIGTERM constraint. Two warnings: MCP registration lives in persisted
`.claude.json`, so the entrypoint needs an idempotent `claude mcp get pal || claude mcp add ...` and
the binary path must stay stable across image versions; and never pass the key via `claude mcp add
-e`, which would persist it in plaintext. Both implemented.

**Q2 — install method.** *Agree with modification.* Rejected vendoring upstream's own Dockerfile
(`python:*-slim` base, venv-across-bases breaks on libpython paths). Because `pyproject.toml` carries
only `>=` bounds, advisor called for `pip freeze` into a committed lock file — otherwise this
recreates the repo's standing unpinned-`npm install -g` debt in Python. Pin to a **commit SHA**, not
a tag. Accepted the ~200–300 MB of unused `google-genai`/grpcio transitive weight rather than
`--no-deps`-ing around it. All implemented; actual delta was +110 MB.

**Q3 — persisted config, seed-if-absent.** *Agree.* Overwrite-on-start "defeats the purpose" — the
owner couldn't edit it. `CUSTOM_MODELS_CONFIG_PATH` must be **absolute**, since a relative default
resolves against the stdio server's CWD. On malformed JSON, PAL gives an empty roster and every call
fails with an unhelpful "unknown model" — advisor asked for a non-blocking validity warning in the
entrypoint. Implemented.

**Q4 — adopt `silent-failure-hunter` and `pr-test-analyzer` now.** *Agree with modification —
decouple the timing.* Agreed on content, disagreed on sequencing: the agent files are a
persisted-mount, zero-image-change, instantly-reversible edit, while PAL is an image rebuild that
ends the session on force-update. Bundling them "holds the trivial safe change hostage to the risky
one." Deferred at the time, then completed separately the same day.

## Two supply-chain findings

1. **The PyPI project `pal-mcp-server` is not the upstream package.** It sits at 10.5.0 — ahead of
   every GitHub signal (`main` pyproject, latest release and top tag all say 9.8.2) — with no author,
   no `project_urls`, no `home_page`, no description, and a release history (10.4.3, 10.4.4, 10.5.0)
   with no continuity with GitHub's 9.x line. Treat it as name-squatted. Install from a pinned git
   SHA only; `test/smoke.sh` asserts nothing installs it from PyPI.
2. **Upstream's `mcp>=1.0.0` is unpinned and resolves to `mcp==2.1.1`, which removes
   `Server.list_tools` and crashes PAL at import.** Pinned to `1.29.1`, with a dedicated static smoke
   assertion guarding that pin specifically.

Also: the repo was **renamed** — `BeehiveInnovations/zen-mcp-server` → `pal-mcp-server`.

## Other findings worth keeping

- `version` and `listmodels` are hardcoded `ESSENTIAL_TOOLS` upstream and **cannot** be disabled via
  `DISABLED_TOOLS`. The live tool surface is **6**, not the 4 the brief assumed.
- PAL's logs go to `Path(__file__).parent / "logs"` — install-relative, not CWD-relative, so no stray
  per-project `logs/` dirs. There is no env var to redirect it.
- `serverInfo.version` reports `9.8.1` while `pip show` says `9.8.2` — a stale upstream string.
  Harmless; do not read it as a wrong-SHA symptom.
- Neither `zai.glm-5` nor `deepseek.v3.2` wraps chain-of-thought in `<reasoning>` tags, so the known
  `gpt-oss-120b` stripping problem does not apply to this roster.
- DeepSeek V3.2's context window is **unverified** — DeepSeek's own docs now cover only v4, and
  secondary sources conflict (128K / 130K / 163,840). `128000` is in use.
- MCP registration is idempotent by design, so a later Dockerfile `ENV` change is **silently inert**
  on an existing persisted home until `claude mcp remove -s user pal` is run. Confirmed live: the
  registered entry still omits `CUSTOM_MODEL_NAME` (it was registered during the proof step, before
  that var existed), and PAL inherits it from the container environment instead. Benign, but this is
  the mechanism to remember if a config change ever appears not to take.

## Post-force-update verification (3 Sep, live)

Everything that could not be proven before the rebuild, now proven:

- Container came back **Up** — worth checking, since restart policy is `no` and a failed recreate
  leaves it stopped.
- PAL runs from the **image-baked** `/opt/pal-mcp`; `claude mcp list` reports `pal: ✔ Connected`.
- `CUSTOM_API_KEY` resolved into the container environment at the correct 132-character length, with
  **zero** literal `!secret` strings in the container env and zero occurrences in `.claude.json`.
- `custom_models.json` on the persisted mount was **not** overwritten — the seed-if-absent logic held
  across a real rebuild.
- All four local agents, `settings.json`, `advisorModel: fable` and the tooling versions survived
  unchanged (Claude Code 2.1.259, Docker 29.7.2, procps present).

## First production run of the counsel — and its first false positive

The pipeline was pointed at commit `b69ff2f`, the PAL change itself. `mcp__pal__consensus` was driven
by **Claude Code's own MCP client**, not a hand-written stdio script — both advisors returned real
completions tagged `"provider": "custom"` from bare on-demand model IDs. The production path works.

The counsel's top-ranked finding was **wrong**, and instructively so.

The local reviewer flagged `templates/claude-code.xml:37` at confidence 78: `CUSTOM_API_KEY` ships
with the literal text `!secret claude-code/bedrock-api-key` while every sibling secret field is
empty, and — correctly, within this repo — observed that nothing in the repo or CI resolves that
syntax, calling it a Home Assistant convention with no unRAID equivalent. `advisor` ranked it **HIGH,
confirmed**.

Verified against the live host, it is a false positive:

- The live template does store the literal 35-character token.
- The live `dockerMan` `Helpers.php` carries five `secretsman` references — [[unraid-secretsman]] is
  patched into the container-create path on that host.
- `my-terrible-butler.xml` uses the identical pattern, the stated precedent.
- The container env holds the resolved 132-character key, not the token.

Resolution happens **at container-create time, by a host plugin outside this repo**. The reviewer
reasoned correctly from everything it could see and was wrong because the mechanism is not visible
from the repository. `advisor` confirmed rather than caught it, having the same blind spot.

**The durable lesson: this review pipeline is repo-scoped, so cross-repo infrastructure dependencies
produce confident false positives, and the triage pass does not catch them — it shares the blind
spot.** Findings that turn on "nothing here implements X" deserve a check against the deployed system
before being acted on.

The residual real point is small: the committed template is only correct on a host running
unraid-secretsman, and neither `OPERATIONS.md` nor the changelog names that dependency. A one-line
note would close it. Separately, the live template has `Mask="false"` and an empty `Description` for
this field where the repo copy has `Mask="true"` — the field was added by hand rather than
re-imported. No secret is exposed by that (the stored value is the token, not the key), but the repo
and live template have drifted.

**On the value question: no.** Across two real reviews the non-Claude advisors have yet to surface a
finding the local reviewer missed. On `b69ff2f` they produced one minor real nit (a swallowed
`claude mcp add` stderr), one cosmetic non-issue, one outright false claim from `deepseek.v3.2`
(that `CUSTOM_API_KEY` is never passed and all authenticated calls must fail — disproven by the same
session's own working tool calls), and several speculative points. The only high-value finding of the
run came from the local reviewer — and even that one did not survive verification.

## Known gaps

- The counsel's cost-benefit is unproven. Two reviews in, the advisors' contribution is one minor nit
  against several false or speculative findings. Worth several more real reviews before deciding
  whether `consensus` earns its place in the routine path or stays a pre-merge-only step.
- `@code-reviewer` chose direct reads over `repository-reader` on `b69ff2f` (279 lines, borderline
  against the ~200-line delegation threshold) and stated the reason in its route line, as designed —
  so the "wait for and use the result" fix, verified once on `butler` `fad1cd1`, has only one
  confirmed exercise.
- Repo/live template drift on `Mask` and `Description` for `CUSTOM_API_KEY`, and the undocumented
  unraid-secretsman dependency.
